# 4better 개발 계획

센서·동영상·상호 승인·정산·광고를 한꺼번에 만들지 않는다. 먼저 **친구들과 목표를 정하고, 기록을 제출하고, 전원이 확인하는 반복 구조**가 실제로 작동하는지 검증한다.

현재 구현 위치는 [`개발_현황.md`](개발_현황.md)에 따로 적는다. 이 문서는 **앞으로 갈 순서**만 고정한다.

문서 기준: 2026년 9월

---

## 권장 전략

전체 제품을 다음 5개 버전으로 나눈다.

| 버전 | 핵심 목적 | 예상 기간 · 1인 |
|---|---|---:|
| V0 | 화면과 핵심 흐름 검증 | 2주 |
| V1 Core MVP | 방·목표·전원 확인·주간 결과 | 8~10주 |
| V1.5 | GPS·건강 데이터 등 목표 확장 | 8~12주 |
| V2 | 광고·구독·포인트 수익화 | 4~6주 |
| V3 | 실제 벌금 수납·보상 지급 | 법률·PG 검토 후 별도 |

센서까지 포함하지 않은 **비공개 베타는 약 10~14주**, 주요 센서 목표까지 포함한 정식 버전은 **약 5~7개월**이 현실적이다.

첫 제품 한 문장:

> 2~4명의 친구가 공부 또는 창작 목표방을 만들고, 기록을 제출해 나머지 전원의 확인을 받은 뒤, 주간 순위와 예상 보상을 확인하고 사진·2초 영상으로 과정을 남기는 비공개 앱.

GPS, HealthKit, 광고, 구독, 포인트, 실제 금전 정산은 이 제품이 **반복 사용**된다는 것을 확인한 뒤에 붙인다.

## 1. V0 프로토타입

기간: 약 2주

실제 서버·센서·결제 없이 전체 사용 흐름만 검증한다. Figma 수준의 프로토타입으로도 충분하다. 이 프로젝트는 Expo 앱으로 같은 화면을 눌렀다.

### 구현 화면

- 회원가입 및 프로필
- 방 만들기
- 초대코드로 참가하기
- 목표 및 주간 목표량 설정
- 페널티와 순위별 분배율 설정
- 규칙 동의
- 목표 기록 제출
- 다른 멤버의 승인·설명 요청
- 주간 순위 및 예상 보상
- 마지막 주차 연장 동의
- 리캡 화면

### 검증할 질문

- 사용자가 방 규칙을 어렵지 않게 이해하는가
- 2~4명이 모두 동의해야 시작된다는 구조가 자연스러운가
- 다른 사람의 기록을 확인하는 과정이 번거롭지 않은가
- 순위별 분배율과 1% 수수료가 명확하게 이해되는가
- 승인 대기, 미인정, 미응답 상태를 구별할 수 있는가

## 2. V1 Core MVP

첫 베타에서는 목표 유형을 전부 넣지 않는다.

### 첫 번째 목표 유형

| 목표 | 선택 이유 |
|---|---|
| 공부·집중 타이머 | 시간 누적형 목표 구조를 검증한다 |
| 글쓰기·그림 제출 | 결과물 제출형 목표와 전원 승인 구조를 검증한다 |

이 두 유형이면 앞으로 필요한 데이터 구조 두 가지를 검증할 수 있다.

- 측정값 누적형: 시간, 거리, 걸음 수
- 제출물 횟수형: 글, 그림, 사진, 방문 인증

생성 화면에 다른 프리셋이 보이더라도, **베타 검증 범위는 위 두 종류**다. 센서 목표는 V1.5다.

### 계정

- 소셜 로그인
- 닉네임과 프로필
- 푸시 알림 동의
- 회원 탈퇴
- 신고 및 차단

### 방

- 2~4명 참여
- 방장 생성
- 초대코드 또는 딥링크
- 시작일과 유지 주수 설정
- 하나의 공통 목표 설정
- 목표량·페널티·분배율 설정
- 규칙 버전 관리
- 모든 멤버 동의 후 시작

### 목표 수행

- 공부 타이머 시작·일시정지·종료
- 앱 종료 후에도 서버 시각을 기준으로 기록 복구
- 글 작성 및 제출 버전 저장
- 그림 사진 촬영 및 제출
- 제출 후 수정 시 새 버전 생성

### 전원 확인

- 본인을 제외한 모든 멤버에게 확인 요청
- 승인
- 설명 요청
- 수정 후 재제출
- 미인정
- 승인자와 처리 시각 기록
- 마지막 한 명의 승인 후 실적 확정

### 주간 결과

- 주간 목표량 대비 달성률
- 확정 기록만 실적에 반영
- 순위 산정
- 동점 처리
- 페널티 예상액 계산
- 총액의 1% 수수료 계산
- 잔여 99%의 순위별 분배 계산

V1에서는 **실제로 돈을 수납하거나 송금하지 않고 계산 결과만 표시**한다.

### 리캡

- 수행 종료 후 사진 1장 촬영
- 2초 영상 촬영
- 촬영 건너뛰기 또는 재촬영
- 비공개 저장
- 승인된 미디어만 리캡에 표시
- 초기에는 자동 영상 편집 대신 날짜순 갤러리

### 기간 연장

- 마지막 주차에 방장에게 연장 제안 알림
- 추가 주수 입력
- 현재 멤버 전원 동의
- 전원 동의 시 종료 주차 연장
- 거절 또는 미응답 시 기존 일정대로 종료

### 최소 관리자 기능

- 사용자와 방 조회
- 신고 조회
- 승인 교착 상태 조회
- 미디어 업로드 실패 조회
- 사용자 이용 제한
- 감사 로그

## 3. V1 개발 스프린트

2주 단위 기준이다. 화면·기반을 병행하면 1인 기준 **10~14주**로 압축할 수 있다.

| 스프린트 | 개발 범위 | 완료 조건 |
|---|---|---|
| Sprint 0 | 정책·화면·DB 확정 | 상태값과 예외 정책 확정 |
| Sprint 1 | 프로젝트 기반·인증 | 로그인, 프로필, 권한 구조 |
| Sprint 2 | 방·초대·규칙 | 2~4명 참가와 규칙 동의 |
| Sprint 3 | 주차·목표 엔진 | 주차 생성과 목표 상태 관리 |
| Sprint 4 | 타이머·창작 제출 | 기록 저장과 버전 관리 |
| Sprint 5 | 전원 승인 | 인원별 필수 승인 계산 |
| Sprint 6 | 결과·분배 계산 | 순위, 페널티, 1% 계산 |
| Sprint 7 | 촬영·리캡 | 사진·2초 영상·업로드 재시도 |
| Sprint 8 | 연장·알림 | 전원 연장 동의와 푸시 |
| Sprint 9 | QA·비공개 베타 | 실제 10개 이상 방 운영 |

다음 작업의 기본 순서는 **아직 닫히지 않은 가장 앞 스프린트**다. 코어가 닫히기 전에 V1.5 센서나 V2 수익화를 본 구현으로 넣지 않는다.

## 4. 공통 목표 엔진

목표마다 별도의 앱처럼 만들지 않는다. 공통 구조를 만들고 측정 방식만 플러그인처럼 추가한다.

```text
목표 템플릿
→ 목표 규칙
→ 수행 세션
→ 측정 기록
→ 증거 자료
→ 전원 확인
→ 확정 실적
→ 주간 결과
```

목표 템플릿이 공통으로 가질 필드:

- 목표 유형
- 단위
- 주간 목표값
- 누적형 또는 횟수형
- 데이터 출처
- 제출 방식
- 증거 필수 여부
- 달성 계산식
- 이상 기록 처리 방식
- 리캡 촬영 여부

세션별 체크 규칙은 [`목표세션_체크기준.md`](목표세션_체크기준.md)를 본다.

## 5. V1.5 목표 확장 순서

센서 목표도 난이도에 따라 나눈다. **V1 베타 기준을 통과한 뒤** 시작한다.

### 1차: 비교적 단순 · 약 3~4주

- 장소 방문(체크인)
- 체중 기록
- 취침 시작과 기상 버튼
- 일반 사진 제출형 목표
- 독서·악기 연습 등 타이머 파생 목표

체크인은 등록 위치 반경, 최소 체류시간, 일일 인정 횟수를 적용한다. 헬스·독서실·공유 오피스는 같은 목표다.

### 2차: GPS 운동 · 약 4~6주

- 러닝
- 걷기 거리
- 자전거
- 등산(레거시. 신규는 워킹으로 흡수)

필수: 위치 권한, 백그라운드 GPS, 이동 경로, 거리·시간, 정확도 필터, 비정상 속도, 일시정지·재개, 오프라인 기록, 배터리 절약 대응.

러닝·자전거는 UI만 다른 기능이 아니다. 이상 기록 판정 기준도 달라야 한다.

### 3차: 건강 데이터 · 약 3~5주

- 걸음 수
- 걷기 거리
- 웨어러블 수면
- 스마트 체중계 데이터

HealthKit과 Health Connect는 출처 구분, 중복 제거, 권한 철회가 필요하다. GPS와 분리해서 개발한다.

## 6. V2 리텐션과 수익화

비공개 베타에서 **최소 4주 이상 재사용되는 방**이 확인된 후 개발한다.

### 구독

- 월 1,000원
- 일반 광고 제거
- 개인·방별 고급 통계
- 구독 복원, 해지·만료
- 서버 영수증 검증

### 광고

- 무료 사용자용 일반 광고
- 사용자가 직접 선택하는 보상형 광고
- 목표 수행·촬영·승인 과정에는 전면 광고 금지
- 광고 완료 이벤트 서버 검증
- 중복 포인트 지급 방지

### 포인트

초기 사용처는 꾸미기로 제한한다. 리캡 테마, 전환 효과, 배경음악, 결과 카드, 프로필 프레임, 방 배지, 스티커, 시즌 한정.

포인트로 살 수 없는 것: 벌금 대납, 보상금 증액, 수수료 할인, 승인권, 순위 보정, 방 추가, 주차 연장, 목표 유형 해금, 현금 출금.

## 7. 실제 벌금·보상금 (V3)

일반 앱 기능 하나를 추가하는 수준이 아니다. **별도 프로젝트**로 본다.

선행: 국내 법률, 앱스토어 정책, PG·정산 파트너, 참가금 보관, 본인인증, 환불·지급 취소, 정산 원장, 중복 지급 방지, 분쟁 시 자금 동결, 탈퇴·제한 계정 지급, 세금·회계.

출시 순서:

1. 벌금과 보상 예상액만 계산
2. 사용자가 외부에서 직접 정산하며 사용성 검증
3. 법률·PG·스토어 검토
4. 제한된 사용자 대상 실제 결제 테스트
5. 문제가 없을 때 1% 수수료 모델 공개

법적 검토 전 빌드에는 앱이 직접 모금·보관·지급하는 기능을 넣지 않는다.

## 8. 권장 기술 구조

| 영역 | 권장 구성 |
|---|---|
| 앱 | React Native + TypeScript (Expo) |
| 서버·DB | Supabase + PostgreSQL |
| 인증 | Supabase Auth |
| 미디어 | Supabase Storage 또는 별도 객체 스토리지 |
| 알림 | FCM + APNs |
| 서버 작업 | Edge Function + 예약 작업·작업 큐 |
| 상태 관리 | TanStack Query + 경량 클라이언트 상태 |
| 오류 추적 | Sentry |
| 분석 | Firebase Analytics 또는 Amplitude |
| 결제 | Apple·Google 인앱결제 |
| 광고 | AdMob |

iOS와 Android를 함께 가져가되, 첫 실기기 베타는 Android부터 한다.

스키마: `supabase/schema.sql`, V1 확장 `supabase/v1_migration.sql`, 목표 enum `supabase/goal_presets.sql`.

## 9. 베타 출시 판단 기준

첫 베타의 성공 기준은 회원 수가 아니라 **방 단위 반복 사용**이다.

- 최소 10~20개 실제 방 생성
- 방 시작 동의 완료율 70% 이상
- 첫 주 목표 기록 제출률 60% 이상
- 제출 기록 확인 완료율 80% 이상
- 승인 요청 후 평균 처리시간 24시간 이하
- 2주차 유지율 50% 이상
- 기간 종료 후 연장 또는 새 방 생성률 30% 이상
- 심각한 개인정보 노출 0건
- 기록·승인 중복 반영 0건

이 기준을 통과한 다음 GPS 목표를 확장한다.
