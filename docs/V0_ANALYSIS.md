# 4better V0 기획 분석

## 제품 가설

4better의 첫 검증 대상은 센서 정확도나 실제 정산이 아니라 다음 반복 구조다.

> 친구 2~4명이 같은 목표와 규칙에 동의하고, 기록을 제출하고, 본인을 제외한 전원의 확인을 받아 주간 결과를 확정한 뒤 다음 주에도 반복하는가?

이 구조에서 가장 큰 이탈 지점은 방 시작 전 전원 동의, 제출 후 전원 확인, 마지막 주 연장 합의다. V0는 세 지점을 눈에 띄는 상태와 짧은 문구로 표현한다.

## V0에 포함한 흐름

1. 닉네임 기반 온보딩
2. 방 만들기 또는 8자리 초대코드 참가
3. 집중 시간 / 창작 제출 목표 선택
4. 주간 목표량과 2·4·6·8주 기간 선택
5. 페널티·순위 비율·1% 계산 예시 확인
6. 규칙 버전 1에 대한 명시적 동의
7. 방 홈에서 확정 실적과 확인 대기 실적 구분
8. 집중 타이머 실행·휴식·종료
9. 메모와 사진·2초 영상 리캡을 포함한 기록 제출
10. 승인 또는 설명 요청
11. 주간 순위와 예상 보상 확인
12. 마지막 주차 연장 동의 또는 거절

## 의도적으로 제외한 범위

- 실제 소셜 로그인과 푸시
- GPS, Health Connect, HealthKit, 백그라운드 센서
- 실제 카메라 촬영과 미디어 업로드
- 광고, 구독, 포인트
- 실제 금전 수납·보관·지급
- 관리자 웹

실제 금전 기능은 법률·PG·스토어 심사 검토가 끝나기 전에는 구현·노출하지 않는다. V0의 금액은 규칙 이해도를 확인하기 위한 예상치로만 표시한다.

## 정보 구조

- 홈: 진행 중인 방, 새 방, 초대 참가, 확인 필요 기록
- 확인: 다른 멤버의 제출물 승인·설명 요청
- 리캡: 승인된 기록을 날짜순으로 보여주는 주간 갤러리
- 내 정보: 프로필과 기본 설정 진입점
- 방 상세: 현재 주차, 확정 실적, 순위, 타이머, 결과, 연장

## 상태 모델 핵심

- 방: recruiting → agreement_pending → active → extension_pending → completed → archived
- 기록: draft → pending_review → confirmed
- 예외 흐름: pending_review → changes_requested → 새 record_version → pending_review
- 거절 흐름: pending_review → rejected
- 연장: pending → 전원 agreed일 때만 approved, 거절 또는 기한 만료 시 기존 종료일 유지

## 데이터 설계 원칙

- 규칙 수정 시 기존 동의를 초기화할 수 있도록 `rule_versions`와 `rule_agreements`를 분리한다.
- 주차 시작 시 참여자를 `week_members`에 스냅샷으로 고정한다.
- 수정 제출은 `record_versions`를 추가하고 이전 승인 결과를 승계하지 않는다.
- 승인 중복은 `(record_version_id, reviewer_id)` 기본키로 막는다.
- 사진과 영상은 `media`에서 종류와 업로드 상태를 별도로 관리한다.
- 모바일 앱은 클라이언트가 만든 달성·정산 결과를 신뢰하지 않고, V1에서 서버 트랜잭션으로 확정한다.

## V0 사용자 테스트 질문

- 전원 동의가 필요한 이유를 설명 없이 이해하는가?
- 확정 실적과 확인 대기 실적을 구분하는가?
- `0/3`이 본인을 제외한 세 명의 확인을 뜻한다는 것을 이해하는가?
- 설명 요청을 거절과 다르게 받아들이는가?
- 1%가 실제 결제가 아니라 예상 계산임을 오해하지 않는가?
- 마지막 주 연장 시 무응답이 동의가 아니라는 점을 이해하는가?

## V1 전환 조건

V0 사용자 테스트에서 핵심 흐름의 완료율과 용어 이해도가 확인되면 Supabase Auth, 실제 방 데이터, 서버 기준 타이머 복구, Storage 업로드 순서로 연결한다. 첫 베타 목표 유형은 집중 타이머와 창작 제출 두 가지를 유지한다.
